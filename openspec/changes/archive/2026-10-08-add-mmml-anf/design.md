# Design

## Context

Мотивация и границы изменения описаны в `proposal.md`, поведение — в `specs/mmml-anf/spec.md`. `MMML/lib/frontend/ast.ml` содержит нетипизированный AST, разделяемый двумя парсерами. Application и lambda бинарны/одноаргументны; `Ast.infix` кодирует оператор двумя application. Menhir допускает bindings операторов, а оба парсера допускают произвольную rhs после `let rec`; вывод типов и interpreter отсутствуют.

`MMML/test/parser_menhir_qcheck.ml` содержит CPS-примеры и генератор для синтаксических свойств, допускающий свободные и некорректно типизированные выражения. `MMML/compiler.ml` печатает AST или запускает самостоятельный LLVM demo; middleend в этот путь ещё не встроен.

Исходники изучены при explore. Техническая основа: `.agents/skills/mmml-compiler/references/anf.md`, лекция `025ANF (2).pdf`, `examples/anf_example.ml`, `examples/anf_qcheck.ml`, справки QCheck и OCaml style. Учебный пример не поддерживает функции и использует целочисленные условия; его семантика не переносится в MMML буквально.

## Goals / Non-Goals

**Goals:**
- Сделать атомарность операндов конструктивным свойством типов IR, а лексические привязки — явно проверяемым контрактом.
- Реализовать детерминированное преобразование без глобального состояния и обязательного предварительного вывода типов.
- Оставить вложенные функции пригодными для анализа свободных переменных в следующих проходах.
- Получать компактный результат при нормализации, не полагаясь на будущую глобальную оптимизацию.

**Non-Goals:**
- Представление замыкания в памяти, соглашение о вызовах backend и построение CFG/SSA.
- Uncurrying неизвестных или пользовательских функций, inlining и удаление произвольных неиспользуемых вычислений.
- Полная проверка типов, общая рекурсия значений или поддержка новых patterns.
- Формат вывода, допускающий обратный разбор исходным парсером; printer предназначен для диагностики IR.

## Decisions

### 1. Separate middleend library

Добавить wrapped library `MMML.middleend` под `MMML/lib/middleend/`, зависимую от `MMML.frontend`. Предлагаемые модули: `Anf` (типы и интерфейс), `Normalize`, `Check`, `Pretty_printer`, а идентификаторы и описание primitives можно выделить в небольшие вспомогательные модули. Публичные контракты документируются в `.mli`; нормализация возвращает `result`, не печатает и не завершает процесс.

Альтернатива — расширить исходный AST и библиотеку frontend. Это смешало бы parsed syntax с ограничениями IR и затруднило последующие проходы. Wrapped library предотвращает конфликт с уже существующим frontend `Pretty_printer`.

### 2. Three levels with compound tail results

IR разделяется на:
- `imm`: int/bool/unit, уникальная локальная ссылка либо внешняя ссылка;
- `compound`: immediate, unary application, primitive с атомарными операндами, unary lambda с ANF-телом, if с атомарным условием и ANF-ветвями;
- `term`: конечный compound, обычный binding с compound rhs и продолжением, отдельный рекурсивный binding функции с телом и продолжением.

Для primitives предпочтительны конструкторы с фиксированной арностью (унарный/бинарный), а не произвольные списки. Checker дополнительно проверяет область видимости; он не заменяет type inference и не пытается определить арность произвольного function value.

Lambda остаётся compound, её тело нормализуется отдельно. Wildcard-параметр получает уникальный внутренний binder без исходных ссылок. Неиспользуемая rhs `let _ = ...` сохраняется как вычисление с неиспользуемым внутренним результатом.

Конечный compound позволяет оставить `f x` без `let t = f x in t`. Альтернатива с возвратом только imm проще для отдельных backend, но создаёт лишние bindings и будет применена позднее лишь при необходимости.

### 3. Unique identity and lexical resolution

Локальные bindings получают уникальные числовые IDs с необязательным исходным именем для диагностики. Внешние ссылки используют отдельный вариант и не могут столкнуться с temporary. Fresh counter создаётся заново на каждый запуск нормализации целого выражения или программы; для всех definitions одной программы он общий.

Окружение связывает исходное имя с внутренней ссылкой или уже известным атомом и информацией о принадлежности builtin. Обычный let нормализует rhs в старом окружении; body — в расширенном. Lambda-параметр затеняет прежнюю привязку. Рекурсивное имя устанавливается перед нормализацией тела. Верхнеуровневые definitions обрабатываются последовательно, не получают неявной видимости будущих definitions.

Начальное окружение содержит явно описанные стандартные операторы; API допускает заданное внешнее окружение. Неизвестные свободные имена сохраняются как внешние ссылки, а checker принимает разрешённые внешние ссылки явно. Использование одного префикса временных строк вместо IDs отклонено: он не обеспечивает отсутствие захвата.

### 4. Continuation-based construction and tail context

Нормализация использует контекст, принимающий атомарный результат (`imm -> term`), для вычислений, чей результат нужен как операнд. Отдельный конечный контекст допускает непосредственно compound, а контекст связывания позволяет сразу записать вычисление под нужным binder без промежуточного temporary и копии.

Константы и ссылки передаются без вычислений. Application нормализует function expression, затем argument, затем строит unary вызов. Порядок задаётся последовательными вызовами явно; код не полагается на порядок вычисления аргументов OCaml.

Let-цепочки строятся продолжениями, а не повторными обходами/конкатенациями хвостов. Алиасы атомов устраняются через окружение; пользовательские top-level definitions и их диагностические имена можно сохранить, не создавая дополнительных административных копий в rhs.

### 5. Structured if with a single continuation

Условие нормализуется первым. Ветви нормализуются независимо в конечном контексте. Если результат нужен дальше, compound if получает один binding, после которого продолжение строится один раз. В конечной позиции if остаётся конечным compound.

Для `h (if c then f x else g y)` результат имеет смысл `let r = if c then f x else g y in h r`. Нормализация не выполняет ветви заранее и не вставляет общее продолжение в обе ветви.

Альтернатива — `Join/Jump`, как в статье Colin James о компиляции lambda calculus. Она полезна для CFG lowering, но добавляет управление join points до появления backend. Структурного if достаточно для текущего контракта; сравнение в условии пока тоже возвращает атом, без дополнительного специального conditional IR.

### 6. Known built-ins and short circuit

Таблица primitives описывает стандартные арифметические, унарные и сравнительные операции. Разрешение binding выполняется до распознавания насыщенного builtin-применения. Известное двухаргументное применение `((+) a) b` переводится в одну бинарную операцию с вычислением a перед b; это допустимо, потому что первое применение именно стандартного арифметического builtin не имеет наблюдаемого эффекта.

Насыщенные известные `&&`/`||` переводятся в structured if: `a && b` означает `if a then b else false`, `a || b` — `if a then true else b`. ANF-вычисления b остаются в нужной ветви. Простые let-алиасы builtin сохраняют его идентичность; затенение именем или параметром снимает это знание.

Значения операторов остаются представимыми внешними function values. Частичное применение сохраняется unary вызовом и вычисляет переданный аргумент сразу. Если builtin проходит через неизвестную higher-order функцию или уже вычисленное частичное применение, общего отложенного вычисления аргументов не вводится: действует обычный strict application. Короткое замыкание гарантировано для насыщенного применения известной привязки, а не для любого неизвестного function value.

Пользовательское `f a b` сохраняется как два unary применения: вычисление/эффект `f a` происходит до b. Объединение по одной лишь синтаксической цепочке или написанию имени отклонено.

### 7. Function-only recursive bindings

Для `Recursive, PVariable f, Lambda (...)` выделяется отдельный рекурсивный binding; имя f доступно в function body и продолжении. Вложенные lambda сохраняют каррирование. Другие recursive rhs и recursive wildcard возвращают явную ошибку неподдерживаемой формы как на уровне выражений, так и на уровне программы.

Это проектное ограничение первого ANF: parser остаётся синтаксическим и не меняется. Реализация рекурсивных произвольных значений потребовала бы правил инициализации, которых у MMML сейчас нет.

### 8. Ordered top-level initialization

ANF-программа — упорядоченный список definitions, в которых нерекурсивная rhs является полноценным ANF term, а рекурсивная definition хранит функцию. Новое имя становится доступно после обычной rhs, либо перед телом recursive function. Список не преобразуется в неупорядоченную таблицу функций.

### 9. Independent verification

Добавить тестовые interpreter для AST и ANF с независимой логикой обхода и общей моделью значений/наблюдаемых builtin-операций. AST interpreter задаёт согласованные source semantics напрямую, не вызывает нормализатор; ANF interpreter исполняет IR. Наблюдение содержит результат, trace эффектов и класс runtime error. Для функций сравниваются наблюдения от применения, не структурное равенство замыканий.

Генератор QCheck строит ограниченные closed/well-typed terms по окружению и целевому типу, включая lambda, application, if, let и shadowing; shrinker сохраняет этот домен. Неограниченная рекурсия не генерируется: recursion покрывается направленными завершающими примерами. Fuel exhaustion фиксируется отдельно и не считается совпадением; число AST/ANF шагов не требуется равным.

Существующие CPS-примеры переиспользуются как source fixtures и дополняются вызовами factorial 5 / Fibonacci 10. Отдельные tests задают порядок trace при получении функции, вычислении аргумента и промежуточном каррированном вызове; оба направления short circuit; ошибку в пропущенной ветви; shadowing операторов; `anf0`; wildcard; локальную и top-level рекурсию/затенение. Checker тестируется также на вручную некорректном IR.

Компактность проверяется по структуре/числу операций и bindings, а не по случайному написанию temporary. Для серии nested if с общим продолжением проверяется линейный рост IR. Printer получает небольшие фиксированные snapshots и тест повторяемости независимых запусков.

## Risks / Trade-offs

- [Без type inference нормализатор принимает часть некорректно типизированных AST] → checker проверяет форму и scope; семантические properties используют корректный домен. Проход не заявляется проверкой типов.
- [Одинаковая ошибка двух interpreter] → независимые обходы, фиксированные ожидаемые результаты/trace и регрессии, помимо differential properties.
- [Устранение bindings может удалить эффект или ошибку] → устранять только административные атомарные алиасы, сохранять application и wildcard rhs.
- [Неточное распознавание builtin нарушит shadowing/порядок] → metadata по binding identity и отдельные проверки alias, shadowing и partial application.
- [Локальная среда OCaml 4.14.2 / Dune 3.20.2 не соответствует Dune language 3.24 и CI OCaml 5.5.1] → не понижать конфигурацию; package-checks выполнять в подходящей среде и отдельно сообщать недоступные проверки.
- [CLI остаётся вне изменения] → библиотечная готовность ANF не выдаётся за готовность полного задания; интеграцию `--stop-after anf` планировать отдельно.

## Migration Plan

Добавить library и тесты без изменения поведения executable/frontend. Прогнать форматирование затронутых OCaml-файлов, `dune b -p MMML` и `dune test -p MMML` в подходящей среде. При откате удаляются новая library и её тесты; существующий parser/CLI не требуют миграции данных. Изменения зависимостей при необходимости вносятся через `dune-project`, не вручную в generated opam.
