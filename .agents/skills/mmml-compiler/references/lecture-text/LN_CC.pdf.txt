1. Введение и терминология
   Во многих языках программирования функции не являются полноценны-
ми first-class citizens: возможности оперировать ими ограничены. Например,
в C можно передавать указатель на функцию в качестве аргумента и возвра-
щать функцию как результат. Однако функции в C не могут быть вложенны-
ми и должны определяться только на верхнем уровне. Это упрощает их реа-
лизацию — по сути, функция в C представляется просто указателем на код.
В функциональных языках (Scala, OCaml, Haskell, Scheme и др.) функции
могут быть вложенными и способны переживать область видимости, в кото-
рой были определены. Это предоставляет широкие возможности (например,
функция может возвращать новые функции), но и усложняет реализацию:
простых указателей на код уже недостаточно.
   Чтобы проиллюстрировать проблему, рассмотрим такой пример на псев-
докоде:

def f(x):
    def g():
        return x
    return g

a = f(10)
b = f(20)
print(a())      # должно напечатать 10
print(b())      # должно напечатать 20



                                            1
    Здесь внутренняя функция g использует переменную x, определённую
во внешней функции f. При двух вызовах f мы получаем два разных экзем-
пляра функции g: a замыкает x = 10, а b — x = 20. В силу лексической
области видимости вызов a() должен вернуть 10, а b() — 20. Чтобы обес-
печить это, необходим специальный механизм: простой перенос x в глобаль-
ную переменную не подходит (иначе оба замыкания вернули бы 20). Этим
механизмом и является замыкание.
    Замыкание (closure) состоит из двух частей: кода функции и окруже-
ния — набора переменных со значениями, которые эта функция захватывает
из внешних контекстов. Создание замыкания можно понимать так: берётся
открытое λ-выражение (функция, использующая свободные переменные) и
снабжается окружением со значениями этих переменных, превращаясь в са-
модостаточный функциональный объект. Обычно замыкание реализуют как
структуру с двумя полями: указатель на код (функцию) и указатель на струк-
туру окружения со значениями всех свободных переменных [1]. Благодаря
этому функция может использовать внешние значения даже после выхода
из исходной области видимости, соблюдая принципы лексической (статиче-
ской) области видимости [2].
    Свободные и связанные переменные. Переменная называется свобод-
ной в функции (λ-выражении) f, если она используется в теле f и при этом
не является ни её параметром, ни локально определённой внутри неё. Фор-
мально, если f = λ(p1 , … , pn ). e и L — множество переменных, объявленных
внутри e, то
            FV(f) = { v ∣ v встречается в e, v ∉ {p1 , … , pn } ∪ L }.
Свободные переменные берутся из внешнего контекста (окружения). Напри-
мер, в примере выше для внутренней функции g переменная x является сво-
бодной, а для f все переменные внутри неё — связанные (параметр x в f
связан). Противоположное понятию свободной — связанная переменная, то
есть параметр или локальная переменная, объявленная внутри функции. Все
свободные переменные функции образуют тот самый набор, который сохра-
няется в её окружении при преобразовании программы.
   Closure Conversion. Closure Conversion (CC, преобразование замыканий)
— этап компиляции, на котором программа переписывается так, чтобы все
функции стали замкнутыми (то есть не содержали свободных переменных).
После CC каждая функция явно получает все необходимые для своего вы-
полнения данные — либо через дополнительные параметры, либо через по-
ля окружения. CC выполняется до финальной генерации кода, обычно на

                                        2
промежуточном представлении программы (например, CPS или ANF). Ча-
сто closure conversion сочетают с lambda lifting: после того как все функции
стали замкнутыми, их можно вынести из вложенных контекстов на верхний
уровень (как глобальные функции). Это упрощает дальнейшую генерацию
кода в языках без вложенных функций (например, на C). Важно не путать
эти два шага: сначала выполняется closure conversion, и только затем, опци-
онально, — lambda lifting [3].
   Два подхода к реализации замыканий. Существуют две основные стра-
тегии, различающиеся организацией окружения и алгоритмом преобразова-
ния [2, 1]:
   • «Плоское» замыкание (flat closure) — хранит все захваченные значения
     непосредственно в объекте замыкания (например, в кортеже или мас-
     сиве слотов) вместе с указателем на код. Окружение интегрировано в
     сам объект замыкания и не ссылается на другие структуры.
   • Замыкание с явным окружением (explicit environment) — хранит окру-
     жение отдельно, как выделенный в куче объект (record) с полями под
     каждую захваченную переменную. В объекте замыкания хранится
     только указатель на такой объект-окружение. Если функция вложе-
     на, её окружение может ссылаться на окружение внешней функции
     (образуя цепочку) вместо дублирования общих данных.
Далее рассмотрены общий алгоритм closure conversion, а затем подробно
описаны два указанных варианта: плоский подход (алгоритм top-down) и
подход с явным окружением (алгоритм bottom-up).


2. Общая схема преобразования (Closure Conversion)
   На этапе closure conversion компилятор переписывает программу так,
чтобы удалить все свободные переменные, введя вместо них явные окру-
жения. Основные шаги:
  1. Анализ свободных переменных. Вычисляется множество FV(f) для
     каждой функции (λ-выражения) в программе. Это делается обходом
     AST: для каждой λ собираются все переменные, которые используются
     в её теле и не объявлены в ней (ни как параметры, ни локально). Если
     функция содержит вложенные λ, их свободные переменные учитыва-
     ются: например, если внутренняя функция использует переменную v

                                     3
  из внешней, то v входит в FV внутренней функции (а значит, v придёт-
  ся сохранить в окружении).
2. Формирование окружений. Для каждой функции, у которой FV ≠ ∅,
   определяется представление окружения. Создаётся структура (запись
   или массив) с полями для каждой переменной из FV. Если FV пусто
   (функция не имеет свободных переменных), окружение ей не требуется
   — такую функцию можно представить просто указателем на код.
3. Переписывание λ-выражений и вызовов. Каждое λ-выражение вида
   (λ (params). body) с ненулевым FV заменяется на выражение, кото-
   рое создаёт замыкание — пару {код; окружение}. Кодом становится
   новая функция, куда свободные переменные добавлены как дополни-
   тельные параметры (чаще всего первый параметр — env, неявный па-
   раметр окружения). Окружение формируется как объект, содержащий
   текущие значения всех свободных переменных. Например:

  λx. x+a+b ⟶ make_closure⒧λ(env, x). x+env.a+env.b, make_env(a, b)⒭ ,

  где make_env(a,b) создаёт объект окружения с полями a = a и
  b = b, а в теле функции используются env.a и env.b вместо ис-
  ходных a и b.
  Все вызовы функций тоже переписываются: вместо прямого вызова
  f(10) выполняется вызов через раскрытое замыкание. Например, вы-
  зов f(x) преобразуется так, чтобы передать функции её окружение:
                 tmp = f;   tmp.code(tmp.env, 10) .
  Здесь мы распаковали замыкание f на code и env, а затем вызвали
  code, передав ему дополнительный аргумент env.
4. Корректность преобразования. После переписывания программа
   должна сохранять исходную семантику. Замыкания гарантируют, что
   каждая копия функции получает собственное окружение с нужными
   значениями, поэтому лексическая (статическая) область видимости не
   нарушается. Инвариант корректности CC: каждое обращение к пере-
   менной в преобразованной программе ссылается либо на локальное
   определение, либо на поле окружения, соответствующее исходной
   свободной переменной, и это поле содержит правильное (лексически
   ожидаемое) значение.

3. Flat Closure Conversion (Top-Down)
Идея плоского замыкания: код + слоты
    Подход flat closure представляет каждое замыкание как единый плоский
объект в памяти: в нём хранятся указатель на код функции и значения всех
её свободных переменных. Реализация такого замыкания обычно подразу-
мевает размещение структуры в непрерывном блоке памяти (например, мас-
сиве), где первый элемент — адрес кода, а последующие элементы — значе-
ния захваченных переменных. Такой объект эквивалентен кортежу: первый
компонент — функция, а остальные — связанные с ней данные.
    При вызове функции, реализованной как flat-замыкание, обращение к за-
хваченным переменным выполняется напрямую через разыменование этого
объекта. Например, если замыкание cl хранит k-ое захваченное значение,
то cl[k] вернёт его. Таким образом, доступ осуществляется за один шаг
(без дополнительных указателей). Цена такого упрощения — больший рас-
ход памяти: каждое замыкание получает собственные копии значений, даже
если одни и те же данные нужны нескольким замыканиям.

Алгоритм Top-Down (спуск сверху вниз)
    Алгоритм closure conversion top-down обрабатывает программу, спуска-
ясь от внешних функций к вложенным. Для каждой функции (по мере обхода
дерева сверху вниз):
   • Вычисляется множество её свободных переменных. Анализ FV можно
     выполнить заранее, либо проводить во время обхода.
   • Если FV ≠ ∅, сразу создаётся структура окружения для этой функ-
     ции. В контексте flat-реализации это означает выделение блока памяти

                                    5
     нужного размера и заполнение его текущими значениями всех пере-
     менных из FV. В переписанном коде вместо исходного λ-выражения
     вставляется выражение, которое создаёт замыкание.
                                                          ′
     λparams. body ⟶ { code = λ(env, params). body ,          env = [значения FV] } ,

     где body’ — это body с заменёнными упоминаниями переменных из
     FV на поля объекта env.

   • Тело функции (body’) преобразуется рекурсивно. Поскольку мы дви-
     жемся от внешнего контекста к внутреннему, к моменту обработки
     вложенной функции её внешняя функция уже преобразована и имеет
     собственное окружение. Если внутренняя функция захватывает пере-
     менную внешней, то при создании её замыкания будет использовано
     текущее значение этой переменной (копия из окружения внешней
     функции). Таким образом, каждое вложенное замыкание получает
     свою копию всех необходимых данных.

Пример: Flat CC (Top-Down)
   Рассмотрим функцию высшего порядка, возвращающую две вложенные
функции, и выполним для неё преобразование по схеме flat.

(* Функция mkPair возвращает пару функций,
каждая из которых использует захваченную переменную x *)
let mkPair = fun x ->
let add = fun y -> x + y in (* первая вложенная функция
 ↩  *)
let mul = fun z -> x * z in (* вторая вложенная функция
 ↩  *)
(add, mul)
in
let (increment, double) = mkPair 1 in
Printf.printf "%d, %d\n" (increment 5) (double 5); (*
 ↩  ожидается: 6, 5 *)

В mkPair обе вложенные функции add и mul захватывают одну перемен-
ную x. После вызова mkPair 1 получаем пару замыканий increment
и double, в каждом из которых должно сохраниться значение x = 1

                                 6
(чтобы increment 5 вернул 6, а double 5 вернул 5). Выполним closure
conversion по схеме flat. Для наглядности введём типы данных для замыка-
ний:

(* Структура Closure: содержит код функции и указатель
 ↩  на окружение *)
type 'a closure = { code: 'a; env: env }
and env = { free_x: int }

Здесь 'a closure — параметризованный тип (тип функции передаётся
как параметр), а env — тип окружения с одним полем free_x для сохра-
нения значения x. После преобразования функция mkPair переписывается
так:

let mkPair = fun x ->
(* Создаем окружение для первой функции *)
let env_add = { free_x = x } in
let add_code = fun env y -> env.free_x + y in
(* Создаем отдельное окружение для второй функции *)
let env_mul = { free_x = x } in
let mul_code = fun env z -> env.free_x * z in
(* Возвращаем два замыкания с разными окружениями *)
({ code = add_code; env = env_add },
{ code = mul_code; env = env_mul })
in
let (increment, double) = mkPair 1 in
(* Вызов функций increment и double с передачей
 ↩  окружений *)
let res1 = increment.code increment.env 5 in (* вызовет
 ↩  add_code с env_add *)
let res2 = double.code double.env 5 in (* вызовет
 ↩  mul_code с env_mul *)
Printf.printf "%d, %d\n" res1 res2; (* выведет: 6, 5 *)

Обратите внимание: при flat-подходе значение x = 1 было скопировано
дважды — в поле free_x окружения env_add и в поле free_x окру-
жения env_mul. Каждое замыкание increment и double хранит свою
собственную копию x. Если бы таких функций было больше или они созда-
вались в цикле, это привело бы к дублированию данных и дополнительным
расходам памяти.

4. Explicit-Env Closure Conversion (Bottom-Up)
Идея явного окружения: объект в куче с полями
   Альтернативный подход хранит окружение отдельно от объекта замыка-
ния. Само замыкание представляет собой пару {код функции; указатель на
окружение}. Окружение — самостоятельный объект (в куче) с именованны-
ми полями под каждое сохранённое значение. Например, на C можно опре-
делить:

struct Closure {
    FunctionPtr code;
    struct Env* env;
};

а окружение описать как структуру Env с полями для нужных переменных.
При создании замыкания выделяется объект Env, и указатель на него сохра-
няется в структуре Closure.
    Главное преимущество explicit environment — возможность разделить
один объект окружения между несколькими замыканиями. Если во
внешней функции определено несколько вложенных функций, захватыва-
ющих одни и те же переменные, компилятор может создать один общий
объект окружения и поместить туда эти переменные. Все вложенные функ-
ции будут хранить указатель на этот общий объект вместо того, чтобы
каждая хранила свою копию. Более того, вложенная функция может хранить
указатель на окружение внешней функции, если ей нужны именно её пере-
менные. В результате окружения могут образовывать цепочку: вложенное
окружение ссылается на окружение внешней функции и т.д., благодаря чему
не происходит дублирования данных.
    Недостаток explicit-env подхода — дополнительная косвенность при до-
ступе к данным. Функции приходится сначала перейти по указателю env, а
затем взять нужное поле. Если окружения связаны цепочкой, для доступа к
переменной внешнего уровня может потребоваться несколько разыменова-
ний. Таким образом, явное окружение экономит память, но потенциально
увеличивает время доступа к захваченным переменным.

Алгоритм Bottom-Up (от внутренних функций к внешним)
   Второй вариант алгоритма CC работает снизу вверх, начиная с самых вло-
женных функций и поднимаясь к внешним. Его логика такова:

   • Сначала преобразуются все внутренние (листовые) λ-выражения. Для
     них строятся замыкания с соответствующими окружениями.

   • Возвращаясь на уровень внешней функции, анализируется, какие её пе-
     ременные были захвачены внутренними функциями. Если вложенная
     функция использует локальную переменную x из внешней, то значе-
     ние x должно сохраниться после завершения внешней функции (ведь
     замыкание может выполняться позже). Поэтому такие x добавляют-
     ся к множеству свободных переменных внешней функции, даже если
     формально x не являлась для неё свободной. Таким образом, внешняя
     функция рассматривается как использующая дополнительные данные,
     необходимые её внутренним функциям.

                                    9
   • Для внешней функции формируется объект окружения, включающий:

       1. её собственные свободные переменные (переменные, которые она
          сама берёт из ещё более внешнего контекста);
       2. переменные, необходимые её внутренним функциям (выявлен-
          ные на предыдущем шаге).

     Если внешняя функция сама является вложенным замыканием и полу-
     чает какую-то переменную через своё окружение, то вместо копиро-
     вания этого значения во внутренней функции можно просто передать
     ссылку на окружение внешней.

   • После определения окружения внешняя функция переписывается: ей
     добавляется параметр окружения, и все обращения в её теле к пере-
     менным из FV (включая те, что нужны только вложенным функциям)
     заменяются на env.field или env->field. К этому моменту её
     тело уже содержит преобразованные вложенные функции (которые со-
     здают замыкания, указывающие на окружения).

   • Алгоритм повторяется, поднимаясь к следующим уровням, пока не бу-
     дет обработана вся программа.
    Bottom-up стратегия требует большего анализа (учёта связей между
функциями разных уровней), но минимизирует дублирование. Общие для
нескольких замыканий значения сохраняются во внешнем окружении один
раз, и несколько функций разделяют один объект окружения. В случае груп-
пы взаимно рекурсивных функций можно создать единое окружение для
всей группы, избежав дублирования и циклических ссылок.

Пример: Explicit-Env CC (Bottom-Up)
    Возьмём ту же функцию mkPair из предыдущего примера, где внутри
определены две вложенные функции add и mul, использующие переменную
x. После выполнения mkPair 1 ожидается, что increment будет прибав-
лять 1, а double умножать на 1. После closure conversion с явными окру-
жениями код mkPair будет выглядеть так (псевдокод):

let mkPair = fun x ->
(* Создаем один общий объект окружения *)


                                  10
let env_shared = { x_val = x } in
(* Код вложенных функций; им добавлен параметр env *)
let add_code = fun env y -> env.x_val + y in
let mul_code = fun env z -> env.x_val * z in
(* Создаем замыкания, оба хранят указатель на env_shared
 ↩  *)
let add_closure = (add_code, env_shared) in
let mul_closure = (mul_code, env_shared) in
(add_closure, mul_closure)
in
let (inc, dbl) = mkPair 1 in
(* inc и dbl - это пары (code_ptr, env_ptr). Вызовем их
 ↩  корректно: *)
let res1 = (fst inc) (snd inc) 5 in (* вызовет add_code
 ↩  с env_shared и 5 *)
let res2 = (fst dbl) (snd dbl) 5 in (* вызовет mul_code
 ↩  с env_shared и 5 *)
Printf.printf "%d, %d\n" res1 res2; (* печатает: 6, 5 *)

Обе функции inc и dbl ссылаются на один и тот же объект окружения
env_shared, внутри которого x_val = 1. Таким образом, x не дубли-
руется — он хранится в памяти единожды и разделяется между этими замы-
каниями. Для сравнения, при flat-реализации этого примера каждая функция
получила бы свою копию x (два отдельных окружения с x = 1). Подход с
явным окружением позволяет сэкономить память и избежать дублирования
данных.
    Обращение к переменной x в теле функций inc/dbl осуществляется че-
рез цепочку указателей: сначала берётся env_shared, затем из него поле
x_val. Если бы уровень вложенности был больше, могла бы потребовать-
ся более длинная цепочка (например, env_inner->env_outer->x), что
несколько увеличивает накладные расходы по времени.


5. Альтернативные подходы
   В дополнение к рассмотренным flat closure и explicit environment суще-
ствуют ещё два важных метода реализации замыканий, применяемых в спе-
цифических сценариях.


                                   11
    Первый метод — дисплей (display) или chain links. При входе в каждую
функцию в глобальном массиве указателей по её уровню вложенности сохра-
няется адрес текущего окружения (активационной записи). Доступ к свобод-
ной переменной реализуется за O(1): компилятор вычисляет индекс уровня
вложенности, достаёт указатель из дисплея и по известному смещению чи-
тает значение переменной. При выходе из функции дисплей восстанавли-
вается, возвращая указатели предыдущего уровня. Дисплей устраняет heap-
окружения и множественные переходы по static link, но требует обновления
массива при каждом вызове и возврате, что накладывает накладные расходы
на выполнение [4].
    Второй метод — явная передача параметров окружения. Вместо со-
здания структур замыкания компилятор добавляет в сигнатуру вложенной
функции все переменные, которые она захватывает из внешнего контекста, и
при каждом вызове передаёт их как обычные аргументы. Рассмотрим пример
преобразования функции mkPair, где внутренняя функция add захватыва-
ет переменную x:

let mkPair = fun x ->
   (* передаём x как явный параметр *)
   let add = fun x_env y -> x_env + y in
   (add x, add)
in
let (increment, add_func) = mkPair 1 in
let result = increment 5 in
Printf.printf "%d\n" result; (* выведет 6 *)

    Здесь add приобретает сигнатуру fun x_env y -> x_env + y, где
x_env — явно передаваемый параметр окружения. При вызове mkPair 1
мы получаем increment как частично применённую функцию add, без
каких-либо структур замыкания. Этот метод устраняет накладные расходы
на выделение и управление окружениями в рантайме, но эффективен толь-
ко при небольшом числе свободных переменных (при большем числе сигна-
туры функций становятся слишком длинными, а функции нельзя безопасно
возвращать за пределы контекста определения) [3].




                                  12
6. Заключение
    В заключение, рассмотренные методы преобразования замыканий де-
монстрируют различные компромиссы между временем доступа, расходом
памяти и сложностью реализации рантайма. На практике современные
компиляторы комбинируют эти подходы с учётом целей и характеристик це-
левого языка. В JavaScript-движках (V8, SpiderMonkey) применяется модель,
близкая к flat closure: для каждой функции создаётся объект Scope, содержа-
щий её переменные и цепочку лексических контекстов [5]. В компиляторах
ML и Scala используют explicit environment с оптимизациями (environment
trimming [6], escape analysis [7]) [8]. В высокопроизводительных реализациях
при необходимости добавляют дисплей для прямого доступа к глубоким
уровням вложенности [4].
