1       Сопоставление с образцом
1.1     Основные подходы
    Сопоставление с образцом (pattern matching, PM) — ключевая часть функ-
ционального программирования, крайне важно уметь ее компилировать эф-
фективно, так как она занимает существенную долю от всего исполнения
программы. Существует два разных способа компилировать сопоставление
с образцом:

      • Автоматы с возвратами — минимизируют размер кода, что влияет на
        скорость исполнения, так как более короткие программы исполняются
        быстрее (статическая стоимость)

      • Диаграммы решений — минимизируют количество проверок, но по-
        рождают более длинный код (динамическая стоимость)

1.1.1    Определение
   Пусть p будет паттерном, а v значением какого-то типа. Значение v под-
ходит под образец p (англ. p matches v) (записывается p ≼ v), если подходит
одно из правил ниже




                                               1
                           _≼v
                           x≼v
                       (p1 |p2 ) ≼ v                 т.т.к p1 ≼ v или p2 ≼ v
              (p1 ; ...; pa ) ≼ (v1 ; ...; va )   т.т.к. pi ≼ vi : ∀i ∈ [1 . . . a]
             C(p1 ; ...; pa ) ≼ C(v1 ; ...; va ) т.т.к. (p1 ; ...; pa ) ≼ (v1 ; ..; va )
    1. Первые два правила говорят о том, что под переменную (имя) или wildcard
       будет подходить любое значение.
    2. Третье правило говорит о том, что под or-паттерн будет подходить зна-
       чение, которое подходит под первый или второй паттерн.
    3. Четвертое правило говорит о том, что под n-ку арности a будет подхо-
       дить значение такой же арности, если все компоненты значения будут
       подходить под соответствующие паттерны.
    4. Пятое правило говорит о том, что под конструктор C с a аргументами
       будет подходить конструктор с таким же именем и такой же арностью,
       если его аргументы будут подходить (см. правило 4).


2      Автоматы с возвратами
2.1     Во что будем компилировать?
   Далее будет приведены конструкции лямбда-кода, которые будут порож-
даться при компиляции PM.
    • let (x1 e1) (x2 e2) ... (xn en) e
        — let необходим для определения имен для подвыражений, который мы
        будет сопоставлять.
      • catch l1 with l2
        Статические исключения exit и ловушки: catch l1 with l2 . Если при оцен-
        ке тела l1 встречается exit, то результатом оценки catch l1 with l2 будет
        результат обработчика l2 , иначе - результат l1 . В отличие от динамиче-
        ских исключений, статические исключения компилируются непосред-
        ственно как переходы к соответствующим обработчикам (плюс некото-
        рое окружение), в то время как ловушки не генерируют никакого кода.

                                                 2
      • switch l with
        case c1: l1
        ...
        case ck: lk
        default: d


        Результатом конструкции switch является оценка li, соответствующе-
        го конструктору ci, являющемуся головным для значения v из l. Если
        головной конструктор v не встречается в списке case, то результатом
        будет оценка выражения по умолчанию d.
        Выражение по умолчанию default: d может быть опущено. В этом слу-
        чае поведение switch для нераспознанных значений будет неопреде-
        ленным. Мы используем ключевое слово switch*, чтобы выделить кон-
        струкции switch без условия по умолчанию.
      • field n x

        — функция получения n-ого элемента n-ки x
      • l1; l2; ()

        Последовательное исполнение и юнит.

   Если ничего из предыдущего не подходит, то матрица P −  → L разрезается
горизонтально на две матрицы P1 −
                                → L 1 и P2 −

3       Диаграмма решений
   В этой секции поговорим о принципиально другом подходе компиляции —
диаграммы решений. Диаграмма решений — это дерево (DAG), где в ли-
стьях результаты, в узлах вычисляется некоторые выражения, а на ребрах
написаны возможные его значения. Для нашего случая в листьях результат
сопоставления, в узле подвыражение, а на ребрах названия конструкторов.
Мы будем строить диаграмму решений, где на каждом из уровней мы будем
сравнивать определенный паттерн. Это гарантирует нам, что мы не будем по-
вторно проводить сравнение для паттернов. Рассмотрим следующий пример.

4    Языки с ленивой семантикой (Haskell)
     В ленивых языках есть понятие еще не посчитанного значения. В Haskell
тип может быть наделен дополнительно расходящимся термом. При попытке
его вычислить программа завершится с ошибкой. Пусть у нас есть функция
or, заданная следующим образом:
(∗ Type of "or" ∗)
or :: Bool −> Bool −> Bool
(∗ Implementation ∗)
or True _ = True
or _ True = True
or False False = False

Если мы попытаемся вычислить её от True и undefined (расходящийся терм),
то получим ожидаемое значение True. Но если в попытке оптимизировать
pattern matching мы поменяем местами первую и вторую строку, то такой вы-
зов упадет с ошибкой, так как в таком случае нам необходимо вычислить вто-
рое значение. В ленивых языках у нас нет свободы в выборе первого столбца,
следовательно в строгих больше простора для оптимизаций.
