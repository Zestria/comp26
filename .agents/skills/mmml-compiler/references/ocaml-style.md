# OCaml: оформление и идиомы

## Источники

Проверено 2026-10-07:
[OCaml Programming Guidelines](https://ocaml.org/docs/guidelines) и
[OCaml 5.5: expressions](https://ocaml.org/manual/5.5/expr.html).
Ниже краткая адаптация для MMML; локальные решения отдельно отмечены.

## По официальным guidelines

Пиши небольшие функции с понятными именами. Слова в именах значений
разделяй `_`; модули и конструкторы начинай с заглавной буквы. Давай имена
сложным подвыражениям и большим callback-функциям. Общую логику выделяй
в функции. Документируй публичный контракт в `.mli`, а в реализации объясняй
нетривиальный алгоритм. Используй исчерпывающее сопоставление с образцом;
для собственных variant types перечисляй конструкторы, чтобы добавление
нового варианта выявлялось предупреждением. Исправляй предупреждения.
Квалифицированные имена помогают избежать неоднозначности; `open Ast`
разумен для модуля, работающего с общими типами дерева.

## Практика текущего проекта

Форматирует OCamlFormat 0.29.0 с профилем `janestreet` из `.ocamlformat`.
Сохраняй этот профиль и стиль соседнего кода, включая расставляемые
форматтером `;;`. В языке `;;` нужен для завершения phrases в toplevel;
не добавляй его механически после каждого выражения `.ml`.
Проверяй только изменённые `.ml`/`.mli`, например
`ocamlformat --check MMML/lib/frontend/location.ml`.
Для `.mly`/`.mll` учитывай возможности установленного форматтера отдельно.
Не форматируй весь репозиторий ради небольшого изменения.

Для AST и IR используй variant types и pattern matching. Разделяй
парсинг, преобразования и печать; не смешивай diagnostics с результатом
прохода. Используй существующий `Error_monad` для ошибок frontend.
Ошибки пользовательской программы возвращай явно; `assert` уместен
для внутренних инвариантов, а не как основной механизм проверки ввода.
Не скрывай ошибки общим `with _ -> ...`.

Предпочитай чистые преобразования дерева. Локальные `ref`, buffers и
hashtables допустимы, если упрощают lexer, генерацию имён или backend;
ограничивай их жизненный цикл одним запуском, когда нужна воспроизводимость.
Не вводи Core/Base ради профиля `janestreet`: используй реальные зависимости.
Не заменяй стандартный `List.map f xs` на вариант другого API без его импорта.

## Семантика языка

OCaml Manual не фиксирует порядок вычисления аргументов application и
правых частей `let ... and ...`. Если действия зависимы, явно используй
последовательные `let`/`;`, а не рассчитывай на наблюдаемый порядок.
Каррированное применение `f x y` означает `(f x) y`; это важно для ANF.
Различай `=` (структурное равенство) и `==` (физическое).
В AST-тестах выбирай структурное равенство или свой comparator с учётом locations.
Ресурсы закрывай и при исключениях; в CLI уже используется
`Fun.protect ~finally:(fun () -> close_in_noerr channel)`.

Порядок вычисления исходного MiniML определяет его собственный контракт.
Не выводи этот порядок из порядка вычисления OCaml-кода нормализатора.
