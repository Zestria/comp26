# Договорённости о RV64 ABI

Статус: **основные договорённости и публичные интерфейсы готовы**.
Константы backend реализованы в `abi.ml/.mli`, объявления runtime —
в `runtime/runtime.h`. Библиотека backend собирается; проверка взаимодействия
с реальным runtime ещё предстоит в ходе реализации и интеграции.

OCaml-доступ к константам: `BDSMl_backend.Abi.Abi`. Имена регистров пока
представлены строками, независимо от будущих типов ассемблера в задаче 3.
Модуль содержит размеры и выравнивание, соглашения о регистрах, значения
bool/unit, смещения полей замыкания и имена публичных функций runtime.

## Цель и инструменты сборки

- Целевая платформа: Linux RISC-V 64, ISA `rv64gc`, ABI `lp64d`.
- Все исходники ассемблера и C runtime собираются с одинаковыми параметрами
  `-march=rv64gc -mabi=lp64d`.
- Значения нашего языка передаются по целочисленной части стандартного ABI.
  Поддержка дробных чисел в `lp64d` не добавляет их в исходный язык.
- `binutils-riscv64-linux-gnu` предоставляет ассемблер и линкер.
- `gcc-riscv64-linux-gnu` собирает C runtime и управляет сборкой и линковкой
  всей программы со стартовым кодом C и libc.
- `qemu-user` предоставляет `qemu-riscv64` для запуска Linux RV64 ELF.
- Выбираем статическую линковку (`-static`) без PIE (`-no-pie`), чтобы запуск
  не требовал отдельного sysroot или параметра QEMU `-L`.

Для Debian/Ubuntu зависимости устанавливаются так:

```sh
sudo apt install binutils-riscv64-linux-gnu gcc-riscv64-linux-gnu \
  libc6-dev-riscv64-cross qemu-user
```

Планируемая команда из корня репозитория после реализации backend и runtime:

```sh
riscv64-linux-gnu-gcc \
  -march=rv64gc -mabi=lp64d -std=c11 \
  -static -no-pie \
  program.s \
  BDSMl/runtime/closures/closures.c \
  BDSMl/runtime/closures/apply.S \
  BDSMl/runtime/io/print_int.c \
  BDSMl/runtime/errors.c \
  -o program.exe

qemu-riscv64 ./program.exe
```

`runtime/errors.c` — планируемый файл реализации `bd_division_by_zero`.
Сейчас runtime содержит заглушки, этот файл ещё не создан, а команда
сборки не проверена на готовой программе. Проверить её и автоматизировать
запуск с ограничением времени нужно в задачах 8 и 10.

## Соглашение о вызовах

Используем стандартное целочисленное соглашение вызовов RISC-V для RV64.
Его соблюдают как сгенерированные функции, так и вызовы C runtime.

- Первые восемь аргументов передаются в регистрах `a0`–`a7` по порядку.
- Результат, занимающий одно 64-битное значение, возвращается в `a0`.
- Аргументы сверх восьми передаются через стек по стандартному соглашению.

Для наших значений используется целочисленная часть выбранного ABI `lp64d`.

## Сохранение регистров и стек

- `a0`–`a7` и `t0`–`t6` могут быть перезаписаны вызываемой функцией.
  Вызывающий сохраняет нужные ему после вызова значения.
- `s0`–`s11` сохраняются вызываемой функцией: если она меняет такой регистр,
  то перед возвратом восстанавливает его исходное значение.
- Вызов перезаписывает `ra`. Функция, которой нужен прежний адрес возврата
  после вложенного вызова, сохраняет и восстанавливает его.
- Функция восстанавливает `sp` перед возвратом. `sp` выровнен по 16 байтам
  на протяжении исполнения согласно стандартному соглашению вызовов.

На первом этапе параметры и локальные переменные хранятся в стековых слотах,
а регистры используются для вычислений и передачи аргументов. Конкретное
расположение слотов и сохраняемых регистров в кадре определяет задача 4.
Глобальные значения требуют отдельного хранения вне кадра функции.

**Обязательное дальнейшее улучшение:** реализовать хранение переменных
в регистрах и аллокатор Linear Scan (линейное сканирование интервалов жизни).
Распределять регистры жадно по интервалам жизни значений, освобождать их
после завершения интервалов и вытеснять значения в стек при нехватке регистров.
Аллокатор должен соблюдать правила сохранения регистров при вызовах.
Стековое размещение — промежуточный этап; эта работа не меняет внешний ABI.

## Представление значений

Каждое значение занимает одно 64-битное слово (8 байт), без тегов типа.

| Значение | Представление |
|---|---|
| `int` | Знаковое 64-битное число в дополнительном коде |
| `false`, `true` | `0`, `1` соответственно |
| `unit` (`()`) | `0` |
| Функция | Указатель на замыкание в памяти |

Одинаковые биты могут представлять значения разных типов, например `0`,
`false` и `()`. Их смысл определяется выполняемой операцией. Динамические
проверки типов этим представлением не предусмотрены; предполагается корректная
по типам исходная программа. Вывод типов остаётся отдельным заданием.

Диапазон целых во время исполнения: от `-2^63` до `2^63 - 1`.
Сложение, вычитание, умножение и арифметическое отрицание работают по модулю
`2^64`: при переполнении сохраняются младшие 64 бита, без исключения.
Сравнения целых используют знаковую интерпретацию.

Литералы в текущем AST хранятся в OCaml `int`, поэтому диапазон принимаемых
литералов ограничен диапазоном `int` компилятора (на 64-битном OCaml:
от `-2^62` до `2^62 - 1`). Это ограничение входа, а не разрядности вычислений
в сгенерированной программе. За пределами диапазона OCaml `int` результаты
RV64-вычислений могут отличаться от результатов запуска исходника через OCaml.
Поведение деления описано ниже в разделе «Печать целых и деление».

## Формат замыкания

Функциональное значение — указатель на начало следующего объекта в памяти.
Все поля и элементы массива занимают по 8 байт.

| Смещение в байтах | Поле | Смысл |
|---|---|---|
| `0` | `code` | Адрес кода функции |
| `8` | `arity` | Полное число аргументов функции |
| `16` | `argc` | Число уже сохранённых аргументов |
| `24 + 8 * i` | `args[i]` | Сохранённый аргумент с индексом `i`, начиная с нуля |

Аргументы хранятся в исходном порядке. Для вызываемого замыкания
`arity >= 1` и `0 <= argc < arity`. Функция без частичного применения
представляется замыканием с `argc = 0`. Определения значений без параметров
вычисляются как инициализаторы, а не как функции нулевой арности.

Например, для `let add x y = x + y` значение `add 5` содержит адрес кода
`add`, `arity = 2`, `argc = 1` и `args[0] = 5`. При последующем применении
к `3` runtime вызывает код `add` с аргументами `5` и `3` по стандартному ABI.
Указатель на замыкание не передаётся как дополнительный скрытый аргумент:
окружение уже представлено явными параметрами после closure conversion.

Частичное применение создаёт новое замыкание и не изменяет исходное.
Сохранённые аргументы должны оставаться доступны после возврата функции,
создавшей замыкание, поэтому их нельзя хранить только в её стековом кадре.

При известной функции и точном числе аргументов backend может генерировать
прямой вызов без создания замыкания.

## Контракт создания и применения замыканий

Публичные C-объявления находятся в `runtime/runtime.h`:

```c
typedef uint64_t bd_value;
typedef void (*bd_code_ptr)(void);

bd_value bd_make_closure(bd_code_ptr code, uint64_t arity);
bd_value bd_apply(bd_value closure, uint64_t argc, const bd_value *argv);
```

`bd_code_ptr` хранит адрес кода, но его C-сигнатура не описывает реальную
арность функции. Вызывать его непосредственно из C нельзя: вызов выполняет
ассемблерный адаптер из `runtime/closures/apply.S`, передавая аргументы
по согласованному RV64 ABI. Интерфейс внутреннего адаптера определяет C.

`bd_make_closure` получает ненулевой адрес кода и `arity >= 1`, создаёт
замыкание с `argc = 0` и возвращает его указатель как `bd_value`.

`bd_apply` получает корректное замыкание и массив из `argc` новых аргументов
в исходном порядке. Сначала идут ранее сохранённые аргументы, затем новые:

- При недостатке аргументов создаётся новое замыкание с их копиями.
  Исходное замыкание не изменяется.
- При точном числе аргументов вызывается код функции и возвращается результат.
- При избытке сначала вызывается функция с нужным количеством аргументов,
  затем оставшиеся аргументы применяются к её результату. В корректной
  по типам программе этот результат должен быть замыканием. Применение
  продолжается, пока новые аргументы не будут исчерпаны.
- При `argc = 0` возвращается исходное замыкание без вызова; `argv` может
  быть `NULL`. При `argc > 0` указатель `argv` должен быть действительным.

Массив `argv` принадлежит вызывающему и действителен только на время вызова.
Runtime не сохраняет этот указатель: аргументы для нового замыкания копируются
в его собственную память. Это позволяет backend размещать массив в стеке.

## Выделение памяти и время жизни

Runtime выделяет новые замыкания в куче через `malloc`. Созданные замыкания
живут до завершения процесса; автоматическое освобождение, подсчёт ссылок
и сборщик мусора на этом этапе не реализуются. Освобождать замыкание после
последнего использования отдельной переменной нельзя: на объект могут
ссылаться другие переменные или замыкания.

При завершении процесса операционная система освобождает его память.
Во время исполнения память под замыкания накапливается: длительное
вычисление с постоянным созданием замыканий может исчерпать доступную память.

Перед выделением runtime проверяет арифметику размеров, включая размер
заголовка и массива аргументов. Проверки переполнения нужны также для
временных массивов и суммирования числа аргументов при применении.
При нехватке памяти или переполнении расчёта размера runtime печатает
понятную диагностику в `stderr` и завершает процесс с кодом `1`.
Эти ошибки не возвращаются как `bd_value`.

Временные буферы runtime, которые не входят в замыкания, освобождаются
после использования. Это не меняет правила времени жизни замыканий.

## Печать целых и деление

Встроенная функция исходного языка `print_int` соответствует символу runtime:

```c
bd_value bd_print_int(bd_value value);
```

Она интерпретирует аргумент как знаковое 64-битное число и печатает его
десятичную запись в `stdout`, без перевода строки. Поддерживается весь диапазон
от `-2^63` до `2^63 - 1`, включая ноль и отрицательные числа. Возвращается
unit, представленный значением `0`. Аргумент и результат передаются через `a0`.

Арность `print_int` равна `1`. При использовании как функционального значения
backend создаёт замыкание с адресом `bd_print_int`, `arity = 1` и `argc = 0`.
Обычный насыщенный вызов может вызывать `bd_print_int` напрямую.

Целочисленное деление выполняется инструкцией RV64 `div`, с округлением
к нулю: например, `7 / 2 = 3`, а `-7 / 2 = -3`.
Особые случаи:

- Перед `div` backend проверяет делитель на ноль. При нуле вызывается
  `_Noreturn void bd_division_by_zero(void)`: runtime печатает
  `division by zero` с переводом строки в `stderr` и завершает процесс
  с кодом `1`. Функция не возвращает управление.
- `(-2^63) / (-1)` возвращает `-2^63`, согласно поведению RV64 `div`.

Арифметика генерируется непосредственно инструкциями RV64. Вызов runtime
нужен только на ветке ошибки деления на ноль.

## Символы, глобальные значения и запуск

Backend генерирует точку входа `main`, вызываемую стандартным стартовым кодом
C при запуске Linux-программы. `main` выполняет глобальные инициализаторы
и выражения `AEval` в порядке деклараций ANF и после успешного завершения
возвращает код `0`. Результаты `AEval` отбрасываются, эффекты сохраняются.

Определения `ADecl` без параметров вычисляются в `main`. Для каждого такого
определения с шаблоном `PVar` выделяется глобальная ячейка размером 8 байт
с выравниванием 8 байт; результат инициализации записывается в неё.
Шаблоны `PUnit` и `PUnderscore` не требуют ячейки, но их вычисления и эффекты
сохраняются. Глобальные ячейки живут до завершения процесса и доступны
из функций независимо от их стековых кадров.

Определения с параметрами порождают код функций; их тела не исполняются
при объявлении. При использовании функции как значения применяется
согласованное представление замыкания.

Alpha conversion уже переименовывает пользовательские привязки, а lambda
lifting вводит имена поднятых функций. ANF сохраняет эти имена в `ADecl`
и `ImmId`. Backend дополнительно сопоставляет им безопасные символы
ассемблера, отделяя их от внешних символов runtime:

| Назначение | Схема имени |
|---|---|
| Пользовательская или поднятая функция | `bd_fn_<номер>` |
| Глобальная ячейка значения | `bd_global_<номер>` |
| Внутренняя метка перехода | `.Lbd_<номер>` |
| Точка входа | `main` |
| Публичная функция runtime | Согласованное имя из `runtime.h` |

Модуль `lowering/symbols.ml` отвечает за таблицу соответствий и уникальные
номера. Генерация имён должна быть детерминированной. Имена из ANF можно
сохранять в комментариях для читаемости ассемблера.

Из встроенных функций исходного языка на этом этапе поддерживается только
`print_int` (символ `bd_print_int`, арность 1). Неизвестные свободные имена
приводят к понятной ошибке компиляции. Поддержка имени в списках встроенных
функций middleend сама по себе не означает его поддержку backend.
